# 单模块 + feature 包边界

状态：已接受（2026-10-25）

项目处于起步阶段，只有一个应用变体与一条构建流水线。首版需要快速验证仓储核心流程，同时避免 `core` 与 `feature` 之间出现循环依赖。若一开始拆成多个 Gradle 模块，配置、依赖注入与构建脚本的维护成本会先于业务收益出现，因此决定使用单个 `:app` 模块，在包层面固定依赖方向：`feature/* → core/*`，feature 之间不互相引用，core 不反向依赖 feature。

## 考虑过的选项

- 多模块（`:core:*`、`:feature:*`）：边界强制更彻底、构建可并行，但当前规模下收益不足以抵消配置成本。
- 按层分包（`ui/`、`data/`、`domain/` 平铺）：同一功能的改动会散落在多个顶层目录，阅读路径变长。

## 后果

- 边界靠约定、代码评审与后续静态检查维持，而不是编译期强制。
- 当 feature 数量、构建时长或并行开发人数达到需要强制边界的程度时，按现有包边界拆模块，业务代码不需要重排。
